# Contract upgrades

`stellar_insights` is the currently governed Soroban contract. Its storage
schema is versioned independently from its executable. Storage keys are append-
only: enum variants must never be reordered or reused. Its configured upgrade
manager is a one-time bootstrap value: the admin can set it once, but cannot
replace it through the bootstrap entrypoint.

## Mandatory upgrade process

Before governance approves a proposal:

1. Build the candidate V2 Wasm.
2. Construct representative V1 state through normal contract operations using
   the actual production `stellar_insights.wasm`.
3. Replace the executable on the same test contract address.
4. Run `realistic_storage_test.rs`.
5. Run `schema_mismatch_test.rs`.
6. Retain the test or CI artifact digest/reference.
7. Record that non-zero evidence reference on the proposal.
8. Only then collect governance approvals.
9. Execute the approved executable replacement.
10. Run the required governance-authorized migration.
11. Validate post-upgrade invariants, including old records and new writes.

The evidence value is an auditable attestation/reference to a test run. It is
not proof generated by the blockchain that a Rust test actually executed. The
on-chain manager enforces that a non-zero reference was recorded before
approval; the Rust tests and CI workflow enforce that the required checks are
run in the repository.

The `Contract upgrade safety` workflow builds the production contract, manager,
candidate, and legacy Wasm fixtures, then fails if the upgrade test suite
fails. Repository
maintainers must mark that check as required in GitHub branch protection; a
workflow file alone cannot configure branch protection.

## Schema policy

Every governed executable has an explicit schema version. Normal state-
dependent entrypoints reject both missing and unexpected schema markers with a
typed schema error. Migration and recovery entrypoints intentionally remain
available during a mismatch, but require the configured upgrade manager and
must name the expected source and target versions.

A fresh `stellar_insights` instance writes schema version `1`. A legacy
instance without a marker is represented as source version `0` only for an
explicit, validated recovery transition; it is never silently treated as the
current schema. The production executable can migrate only `0 -> 1` and `1 ->
1`; it cannot relabel storage to an arbitrary version. A candidate executable
must explicitly understand the source layout and may write only its own
implemented target schema. The marker is written only after required legacy
state has been validated. Replacing Wasm does not migrate storage.

The generic upgrade manager validates only generic proposal fields such as a
non-zero target schema. The governed executable is the authority on storage
compatibility and transition validity.

## Bad-upgrade remediation

Rolling back executable Wasm does not roll back storage mutations made by a bad
upgrade. Operators must:

1. Stop or block normal operations where possible.
2. Identify the last known-good schema and state.
3. Deploy known-good or dedicated repair Wasm that contains explicit repair
   logic for the identified source layout.
4. Execute a governance-authorized repair migration.
5. Reconstruct corrupted values from authoritative sources if necessary.
6. Verify storage invariants.
7. Write the correct schema marker only after repair succeeds.
8. Resume normal operations.

Executable rollback alone is insufficient, and a generic schema-marker rewrite
is not remediation. Irreversible corruption may require off-chain
reconstruction. A future rollback may therefore require a dedicated recovery
Wasm with migrations it actually implements. Every governed version must
preserve the stable upgrade and recovery ABI so that this procedure remains
possible.
